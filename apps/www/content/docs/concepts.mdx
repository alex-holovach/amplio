title: Core concepts
description: Events, Plugins, declared trees, observations, and delivery.
---

Amplio has two semantic concepts: **Event** and **Plugin**.

## Event

An Event is a versioned, schema-validated semantic record with runtime identity.

```ts
const HttpRequest = event({
  id: "http.request",
  version: 1,
  schema: z.object({
    request_id: z.string(),
    http: z.object({
      method: z.string(),
      route: z.string(),
      status: z.number().int().optional(),
    }),
  }),
});
```

The same `event()` primitive defines roots and nested occurrences:

```ts
const ProviderCall = event({
  id: "provider.call",
  version: 1,
  schema: z.object({ provider: z.string() }),
  timing: "duration",
  cardinality: { many: { max: 16 } },
});
```

- `timing: "instant"` records semantic state at one point.
- `timing: "duration"` adds `duration_ms`, `success`, and structured failure state.
- A single Event reserves at most one occurrence.
- `{ many: { max } }` produces a bounded invocation-ordered array.

Nested Events are optional in traffic. Declaring a Plugin branch means the branch is allowed to
contribute; it does not force every request to use that provider.

## Plugin

A Plugin attaches Events to one native seam and owns the projection from native data into safe,
stable semantics.

```ts
const ProviderPlugin = plugin({
  id: "provider",
  events: { calls: ProviderCall },
  instrument({ events, observe }) {
    return function instrumentProvider(send) {
      return observe(events.calls, send, {
        input: ({ args: [input] }) => ({ provider: input.provider }),
      });
    };
  },
});
```

`ProviderPlugin` is callable at its native seam and exposes its exact Event definitions on
`ProviderPlugin.events`.

A Plugin has one of two roles:

- A contributor Plugin observes a provider or local function and is mounted in a root Event tree.
- A boundary Plugin owns a framework or worker lifecycle and opens a root Event.

Those are roles of the same concept, not separate public APIs.

## Declared tree

A root Event declares every possible branch before application code runs:

```ts
export const HttpRequest = event({
  id: "http.request",
  version: 1,
  schema: HttpRequestFields,
  tree: {
    auth: BetterAuthPlugin.events,
    email: ResendPlugin.events,
    database: DrizzlePlugin.events,
  },
});
```

Plain objects create structure. Every leaf is an exact Event definition exported by a Plugin. Tree
keys choose record placement; semantic IDs do not.

Definition identity matters. Recreating another Event with the same `id` does not grant it access
to a declared slot. This prevents unrelated code from writing into a branch by string coincidence.

## Observation

An observation is one runtime occurrence of a mounted nested Event. Plugin tools create
observations:

- `record(...)` for instant Events;
- `observe(...)` for ordinary function calls;
- `begin(...)` for callback and hook lifecycles.

These tools exist only inside `plugin({ instrument })`. Application code cannot retrieve an active
Event or mutate it directly.

## Lifecycle

`RootEvent.handle(fn, projectors)` opens a root, runs `fn`, and finalizes when the returned value or
native Promise settles. Frameworks whose true completion happens in hooks use `openEvent()` inside
an open-code boundary Plugin.

The root closes exactly once. Pending nested observations are omitted from the immutable snapshot
and diagnosed; later completion cannot mutate delivered data.

## Sink

A sink is operational delivery configuration, not semantic authoring. Every kept root record is
sent to configured sinks after sanitization, redaction, and sampling.

```ts
init({
  service: "orders-api",
  env: "production",
  sinks: [consoleSink, otlpSink],
});
```

Sink failures are isolated from application behavior and from later sinks.
