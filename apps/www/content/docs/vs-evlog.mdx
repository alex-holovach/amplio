---
title: vs evlog
description: Same wide-event ambition, different ownership and composition model.
---

evlog and Amplio both prefer one rich event over scattered prose logs. The main difference is who
owns semantic state.

|                        | evlog                                        | Amplio                                             |
| ---------------------- | -------------------------------------------- | -------------------------------------------------- |
| Primary interface      | Request-scoped mutable logger context        | Versioned Event definitions and native Plugins     |
| Application call sites | Add fields during execution                  | Call ordinary functions                            |
| Shape ownership        | Emerges from mutations across the call graph | Declared in one root Event tree                    |
| Reuse                  | Shared conventions and logger helpers        | Exact Plugin Event definitions mounted by identity |
| Lifecycle              | Logger scope and explicit field updates      | Boundary Plugin closes automatically               |
| Provider semantics     | Caller adds fields around provider use       | Plugin wraps provider construction once            |

## evlog style

```ts
const log = useLogger(event);

log.set({
  user: { id: user.id, plan: user.plan },
});
```

This is compact and useful when the code doing the work should directly annotate a request-scoped
context. The final shape, however, is distributed across every call site that mutates it.

## Amplio style

The application call remains native:

```ts
const payment = await charge(input);
```

Open code wraps that exported seam once:

```ts
export const StripePlugin = plugin({
  id: "stripe",
  events: { charges: Charge },
  instrument({ events, observe }) {
    return (charge) =>
      observe(events.charges, charge, {
        input: ({ args: [input] }) => ({
          amount_cents: input.amountCents,
          currency: input.currency,
        }),
        result: ({ result }) => ({ payment_id: result.id }),
      });
  },
});
```

The root declares placement:

```ts
export const Checkout = event({
  id: "checkout",
  version: 1,
  schema: CheckoutFields,
  tree: {
    payments: StripePlugin.events,
  },
});
```

The Plugin can contribute only when its exact definitions are mounted in the active root. It cannot
write arbitrary fields into an undeclared branch.

## Why Amplio chooses declaration

The Event file answers these questions without running the application:

- Which provider semantics can appear?
- Where do they appear in the final record?
- Which schema and wire version govern each node?
- Is a nested Event timed or instant?
- Is repetition bounded, and by how much?
- Which native source owns projection and privacy choices?

This is the same reason schema-first APIs are easier to review than mutable bags: the possible
output is visible before execution.

## What Plugins cost

Amplio asks for an explicit native seam and editable wrapper source. That is more setup than calling
`log.set(...)` wherever data is available. It also means a provider without a stable, observable
seam may need a custom Plugin or may not be a good fit.

The trade is deliberate: more meaning in one reviewed place, less telemetry state in application
code.

## What both approaches share

- wide events are usually more useful than fragmented prose;
- stable semantic fields beat parsing messages;
- errors and latency belong beside business context;
- privacy requires explicit field selection and redaction;
- logs and traces can be exported together rather than treated as rivals.

Choose evlog when direct request-scoped annotation is the desired programming model. Choose Amplio
when application calls should stay ordinary and the repository should declare the full Event tree.
