## evlog

**Same wide-event model. Different ownership model.**

| | evlog | amplio |
|---|---|---|
| Code location | Closed npm runtime + optional augmentation | Open `telemetry/` in your repo |
| Event model | Logger methods + modules | Schema-first `defineEvent` + wide events |
| Install | npm package | CLI scaffolds editable files (shadcn-style) |
| API surface | `log.info`, plugins, etc. | Frozen: `defineEvent`, `init`, `getLogger`, `.child()`, `.set()` / `.error()` / `.emit()`, `flush()` |
| After setup | Runtime dependency you update via npm | CLI is removable — only `@useamplio/amplio` stays installed; you keep editing `telemetry/` |

amplio is **not** evlog. You own the schemas, middleware, sinks, and integrations — they scaffold as readable, typed files under `telemetry/` that you can diff in PRs. The runtime (`@useamplio/amplio`) is ~4.5 KB gzipped with zero runtime dependencies (optional `zod` peer). If you'd rather have telemetry logic updated for you through npm than own it in your repo, a closed runtime is the simpler trade — amplio optimizes for the opposite: telemetry changes go through your code review.

## vs printf logging

```typescript
// ❌ not amplio
log.info("user signed up", { userId });

// ✅ amplio
getLogger()
  .child(AuthUserSignedUp)
  .set({ user: { id: userId }, signup: { method: "email" } })
  .emit();
```

Structured fields come from Zod schemas — not ad-hoc objects.

## vs OpenTelemetry traces alone

amplio emits **wide events**: one rich JSON record per request or domain action. Traces answer "what happened in this span tree"; wide events answer "what happened in this business unit of work" with schema-validated fields you define.

OTLP sink exports to your collector when you need both.

## When to pick amplio

- You want observability code in PRs, not black boxes
- You prefer one emit per request/job with accumulated context
- You use shadcn-style registry installs
- create-t3-app / Hono / Express / Fastify with minimal wiring
